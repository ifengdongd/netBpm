5浏览器设计器方案

选 bpmn-js + 自定义 moddle 扩展，不自研画布 —— 因为「照搬 Activiti 定义」这件事几乎零成本

为什么是 bpmn-js

  • 格式天然对齐：bpmn-js 是 BPMN 2.0 的参考实现级工具链，它输出的 BPMN 2.0 XML + BPMNDI 正好就是 Activiti 转换器的输入契约。自研画布反而要重新对齐一遍格式。
  • 与 Activiti 同源：Activiti 6 之后官方即采用 bpmn-js 替代早期基于 Oryx 的 Activiti Modeler。
  • 省 3–4 人月：拖拽、连线、吸附、对齐、撤销重做、导入导出、缩放平移全部自带。

需要自己做的五件事

  1. activiti-moddle.json 描述符 —— 声明 activiti: 命名空间下的全部属性。没有它，bpmn-js 会在往返中丢掉这些属性。
  2. 调色板裁剪 —— 只留子集元素，移除其余按钮。
  3. 属性面板 —— 顺序流条件表达式 + 默认流开关；用户任务办理人/候选组；服务任务实现方式三选一。
  4. 即时校验 —— 前端高亮 + 后端 Bpmn.Validation 复校（前端校验只是体验，不能作可信边界）。
  5. 只读实例视图 —— 复用 Viewer + ACT_HI_ACTINST 着色。

契约只有两个端点：POST /api/designer/deploy（提交 BPMN XML）、GET /api/designer/definition/{id}/xml（回显）。设计器不直接操作数据库，一切经后端解析 → 校验 → 落库。

技术栈：TypeScript + Vite + bpmn-js@18 + bpmn-js-properties-panel，打包为可嵌入的 Web Component / iframe。

6运行时语义：两条必须照搬的 Activiti 特有行为

这两条不是 BPMN 规范原文，是 Activiti 的实现选择 —— 照搬它们才能保证同一份流程在两端行为一致

① 排他网关：取「第一个条件为真」

源码依据：ExclusiveGatewayActivityBehavior.leave()

  • 遍历出口流，取第一条「条件为真且不是 default」的流 → 立即停止选择
  • 都不满足 → 走 default 流
  • 连 default 都没有 → 抛异常
  • ⚠️ Activiti 没有「多条件同时为真则报错」的检查（BPMN 规范建议报错）—— 不要「顺手加个校验」，那会导致两端不一致

② 并行网关：按「入流条数」计数

源码依据：ParallelGatewayActivityBehavior.execute()

类注释中明确写了这是对规范 p.436 的有意偏离：「if two tokens would arrive through the same sequence flow, our implementation would activate the gateway」

  • 先 inactivate() 把自己置为非活动
  • 查「当前活动 = 同一网关」的非活动执行数
  • 判定用 总数相等（≠ 每条流都到过）
  • ✅ 到齐 → 删除其余执行 → Fork
  • ⏸️ 未到齐 → 什么都不做，静默等待
  • ⚠️ 并行网关出口 不做条件判定

推进模型：Agenda + Operation（不要写成递归）

三处相对 Activiti 的「现代化」改动

改动Activiti本方案理由
异步模型同步阻塞全链路 ValueTask .NET 原生；但必须保持「单命令内同步排空 Agenda」，否则语义漂移
上下文传递ThreadLocal + Context 静态类AsyncLocal<CommandContext> .NET 下 ThreadLocal 在 async 续体间会丢/串。加分析器规则禁止 [ThreadStatic]
变量序列化Java 原生序列化 → ACT_GE_BYTEARRAYJSON (System.Text.Json) Java 序列化产物 .NET 读不了；JSON 兼具可读性与跨语言性

沿用表结构的四项收益

  • 零设计成本 —— DDL 直接取 Activiti 建表脚本的子集
  • 对拍可行 —— 两端读写同一表结构 → 可做库级 dump 差异比对（最强验证手段）
  • 灰度可行 —— 同一套库，Java 跑存量 / .NET 跑新增
  • 生态复用 —— 基于 ACT_* 的报表、监控工具可直接用

⚠️ ID 生成器必须逐行对齐

Activiti 9 默认 DbIdGenerator：从 ACT_GE_PROPERTY 读 next.dbid，一次性占走一个区块（idBlockSize，默认 2500），进程内自增发放，用尽再占下一块。

若改成 UUID 或数据库自增，两端 ID 空间不同，对拍的库级 diff 会全线失败。

初值：('schema.version','8.1.4',1)、('next.dbid','1',1)

9质量方法：对拍验证（Differential Testing）

把 Activiti Java 版当作「预言机」—— 这是「照搬语义」策略最核心的红利，比自建基准便宜一个数量级

② 是杀手锏。因为沿用 ACT_* 表名与列名，两端跑完后可以直接 dump 所有行做逐列比对 —— 这能捕获 API 层看不出的执行树内部差异：IS_CONCURRENT_ / IS_SCOPE_ 标志位错、子执行多建/少建、Join 时该删的执行没删。

若当初选了「自定义表结构」，这一整套验证手段都不可用，只能退回到靠 API 返回值猜内部状态。这正是沿用表结构那个决定的真正价值。

10风险登记与对策

风险高低不是按「技术难不难」排，而是按「出错后能不能被发现」排

#风险概率影响等级对策
R1并行网关同步语义实现偏差（计数逻辑、inactivate 时机、Join 后删除哪些执行） 高高极高 唯一致胜手段：死磕对拍。把 5 个步骤 + ACT_RU_EXECUTION 行快照作为硬门禁，不通过不进入下一阶段

R3执行树标志位组合错误（isActive / isConcurrent / isScope） 高高高 不用「最终状态」验收，改用树形快照对拍（每步都 diff）；写标志位不变量断言
R4async/await 与 Agenda 排空的交错 中高高高 硬约束「单命令内同步排空 Agenda」；分析器禁止 [ThreadStatic]；AsyncLocal 上下文专项测试
R5设计器往返丢属性 / 丢 DI 中中中 activiti-moddle.json 描述符必须先行；P8 验收含「往返保真」断言；设计器导出的 XML 全部纳入 P2 回归集
R6范围蔓延 —— 有人要加子流程 / 多实例 / 会签 高高最大管理风险 12 条「不做」写成书面签字基线；任何追加走变更评审并重算人月。引擎项目最常见的死因就是这个，不是技术
R7存量 Java 数据 / 流程迁移 中中中 表结构同构已大幅缓解；变量序列化差异（Java 序列化 vs JSON）需工具转换；若确需迁移，单独立项

12需要你确认的 4 个问题

这 4 项会影响人月与架构，建议在 P0 阶段落定

#问题影响
1「同步执行」的口径：是否就是并行网关（AND）的分叉 + 同步合并？ 若有「外部回调等待」含义，需追加语义设计
2是否需要「会签 / 多实例」？multiInstanceLoopCharacteristics 已列入不做，但它是审批场景最高频的追加需求。 若确定需要 → +2.5 人月，并提前到 P6 一并设计
3是否沿用 ACT_* 表结构？这是对拍能力的基础。 若改为「自定义表 + EF Core」→ +1.5 人月，且永久失去库级对拍能力
4设计器宿主形态：独立 Web 应用，还是必须嵌入现有业务系统？ 若需嵌入（Web Component / iframe）→ P8 +0.5 人月做集成适配
